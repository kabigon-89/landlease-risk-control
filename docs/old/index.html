01目的

システムが担う定型審査・期日統制と、職員が担う専門的判断の 責任分界点を明確にする。

AI はリスクの所在を示す壁打ち相手に徹し、最終判断は常に職員が行う。人事異動を前提とした組織で、職員が萎縮せずに本来の専門的判断へ集中できる状態をつくることを主軸に置く。

心理的安全性の確保

見落としへの不安を定型チェックと期日統制で受け止め、着任直後でも判断に踏み込める状態にする

業務効率化

期日管理・条文の一次チェック・検算を代替し、繁忙期のピーク業務量と教育コストを圧縮する

内部統制の強化

職務分掌と監査証跡を設計に組み込み、判断の根拠と経緯を事後に追跡できる状態を担保する

効率化そのものではなく、構造的な不安を取り除くことが目的である点を最初に置きます。

02業務課題定義

属人化した条項審査と期日管理に、構造的なリスクが内在する

01

期日管理の不備

更新時期の管理が個人の Excel に依存。事前通知期限は契約ごとに異なる。

無契約状態での不法占有／意図しない自動更新／延滞金の発生

02

条項リスクの見落とし

過去案件の流用により必須条項が欠落。義務規定と任意規定の混同も生じる。

相手方への抗弁権の付与／明渡時・地代改定時の紛争

03

知見の非定着

数年ごとの異動で借地借家法の知見が組織に残らず、経緯は個人の記憶に埋没する。

算定ミスによる公金の過不足／過去の是正要請の看過

実務で観測した 3 つの課題。いずれも財政的・法的リスクに直結します。

03課題への対応策

課題を、定型処理と判断支援に切り分けて手当てする

課題対応策担う基盤
期日管理の不備 更新・支払・変更解約の各期限をチケット化し、所管課と資産経営課へ段階的に通知する ServiceNow
条項リスクの見落とし 法令・自治体規則を参照して条文リスクを抽出し、大きさと理由を提示。受容か修正かは職員が判断する Azure
知見の非定着 契約書に残らない経緯・却下理由をナレッジとして蓄積し、RAG によって次回判定の材料とする Azure
課題ごとに、どの基盤がどこまで担い、どこから職員が判断するかを対応させています。

04スコープ定義

行政が貸主となる土地賃貸借契約に限定する

対象に含める

  • 普通借地（更新のある借地権）
  • 定期借地（一般・事業用・建物譲渡特約付）
  • 借地借家法の適用のない土地貸付（駐車場・資材置場等）
  • 新規契約の起案（案文作成〜所管課確認の記録）
  • 期間中の更新・条件変更・終了判断の支援

対象外とする

  • 行政が借主となる契約／使用貸借／売買／借家
  • 起案書に対する上長承認（決裁）
  • 相手方との条件交渉・合意形成そのもの
  • 契約終了後の明渡し・原状回復の履行確認

固定資産台帳等の既存システムとの自動連携は行わず、CSV ／ Excel エクスポートで庁内資料に活用する。

対象を絞り切ることで検証可能性を確保しました。対象外を明示するのがポイントです。

05システム全体構成

定型ワークフローと非定型な判断支援を、基盤ごとに分担する

ServiceNow

定型的なワークフロー・期日管理

更新期限・支払期限・事前通知期限・年次現況報告の期日を管理し、期限到来前にチケットを起票。案文確認や更新可否判断も、依頼〜回答をステータスとして記録する。

Flow Designer / Scheduled Flow / Task テーブル / ACL ＋ Roles

API 連携

Azure

非定型な判断支援（リスク抽出・金額検算）

条文を解析し、法令・自治体規則と照合してリスクを抽出。算定ロジックはコード実行環境で計算し、算術的な正確性を担保する。

Azure OpenAI / AI Search / Container Apps / Blob Storage / Monitor

データフロー

案文アップロード → Azure でリスク抽出・検算 → 結果を ServiceNow に書き戻し → 所管課への確認依頼・回答をチケットで管理

性質の異なる 2 つの処理を、それぞれ適した基盤に分担させています。

06職務分掌とアクセス制御

起案・政策判断・最終承認を、それぞれ別のロールに分離する

起案・事務処理

資産経営課 職員

案文の起案、リスク抽出結果の受容／修正の判断、所管課への確認依頼、更新・変更・終了の事務処理

人事異動情報と連動しロールを自動付与

政策判断

所管課 職員

起案時は現場目線での案文確認（確認済み／差し戻し）、更新時は更新／変更／終了の判断とその理由

案件単位で閲覧・回答権限を付与

承認

資産経営課長

高リスク判定が出た案件の最終承認、システムの権限設定など監査対応上必要な承認

一職員の判断のみでの成立を防止

いずれも RBAC（Entra ID 連携）で付与し、所管課職員は自身が関与する案件以外の契約情報にアクセスできない。

起案と承認、事務処理と政策判断という 2 つの分離を設計に埋め込んでいます。

07IT 全般統制・AI ガバナンス

プロンプトとモデルも、構成管理と監査証跡の対象に含める

変更管理

インフラ構成は IaC、反映は CI/CD による自動テスト・レビュー・承認を経る

AI への指示内容は変更者・日時・理由・差分を記録し、判定基準の変更を追跡可能にする

モデルバージョンは固定し、切替は既存判定との比較検証を経て行う

監査証跡

「誰が・いつ・何を・なぜ」の 4 項目を最低限含む形式で記録する

業務上の意思決定、AI の判定結果と職員の受容／修正、権限付与履歴、システム変更履歴を対象とする

追記のみ可能なログとして保持し、保持期間は文書管理規程に準拠する

セキュリティ・AI 固有

個人情報を含むデータは学習利用されない設定とし、処理範囲を Azure 環境内に限定する

文書内容と指示を構造的に分離し、プロンプトインジェクションに備える

判定には一次情報の該当条文へのリンク・引用を必ず併記する

AI を業務に組み込む際の統制。プロンプトとモデルバージョンも構成管理の対象に含めています。

08ガバナンスフレームワークとの対応

COBIT の EDM を軸に、NIST CSF・ISO 27001 と対応づける

COBIT（EDM） 本システムにおける対応 NIST CSF の対応機能 ISO/IEC 27001 の対応区分
Evaluate評価 AI による条文リスク抽出・金額検算により、契約に内在するリスクを定型的に評価する Identify 契約に内在するリスクの識別・評価 組織的管理策（リスクアセスメント）
Direct指示 受容か修正かは職員が判断し、高リスク案件は課長が最終承認することで、組織としての意思決定を方向づける Govern ／ Protect 職務分掌・アクセス制御による予防的統制 組織的・技術的管理策（アクセス制御、権限管理）
Monitor監視 監査証跡と異常検知の仕組みにより、意思決定とシステム運用の適切性を事後・継続的に検証する Detect ／ Respond 異常の検知と対応 技術的管理策（ログ取得及び監視）

ガバナンス目標（COBIT）を上位に置き、実装レベルの統制を NIST CSF の機能・ISO/IEC 27001 の管理策区分に紐づけることで、監査時の説明可能性を確保する。

設計の考え方を COBIT の EDM に整理して、統制の説明可能性を担保しています。

09AI リスク抽出・金額検算

検出すべき観点を定め、確信度の低い判定に確認を促す

最低限のチェック観点

  • 必須条項の欠落（用途制限・土壌汚染対策・原状回復義務）
  • 義務規定と任意規定の混同
  • 「著しく」等の定性表現の残存
  • 相手方に有利な抗弁権を与える条項
  • 地代等の算定根拠の明記
  • 参照法令における情報源の相違

信頼度スコアと職員への扱い

高　80% 以上

通常の確認で問題ない

中　50 〜 80%

通常通り確認し、特別な強調表示はしない

低　50% 未満

重点確認を促す強調表示を行う

金額検算は、LLM が算定ロジックを組み立て、計算はコード実行環境で実行することで算術的な正確性を担保する。

最低限のチェック観点と、信頼度スコアによる重点確認の促し方です。

10フィードバックループ

職員の却下理由を、次の判定材料として組織に残す

  1. STEP 1

    判定の提示

    リスクの大きさ・理由・信頼度スコア・根拠条文へのリンクを提示する

  2. STEP 2

    却下理由の記録

    「リスクではない」と却下する場合、理由の入力を求め記録する

  3. STEP 3

    ナレッジへの反映

    却下理由・修正履歴をベクトル化し、以降の RAG の参照材料とする

  4. STEP 4

    精度のモニタリング

    却下率・その推移・信頼度スコアとの相関を継続的に検証する

却下率が閾値を超えて上昇した場合は、知識ベースやプロンプトの見直しを検討するトリガーとする。蓄積は通常業務の入力から自動的に取り込まれ、職員に追加作業は生じない。

却下理由をナレッジに戻すことで、同種の誤検知を抑制します。

11TCO と効果

年間 20 件では投資に見合わない。それを前提に設計している

236万円／年

年間 TCO（仮）。コア 7 名のフルライセンス、所管課の軽量ライセンス、Azure 費用の合計

20件／年

土地貸付契約の処理件数。対象が明確でリスクの性質を検証しやすい最初の適用領域

1 〜 4月に集中

繁忙期。定員は閑散期基準のため応援要員への依存と教育コストが常態化している

定性的効果暗黙知の条項欠落による追加費用、算定誤りの長期未発覚といった実際の損失事例が、必要性を裏付けている

定量的効果提案段階のため達成目標（仮説）として位置づけ、パイロット運用を通じて実測・検証する

単体では投資に見合わないことをまず認め、その上で拡張前提の設計であることを示します。

12今後の拡張性

期日管理・リスク抽出・ナレッジ蓄積を核とする統制基盤として展開する

A

対象文書の横展開

建物賃貸借・売買・物品調達・業務委託、仕様書や RFP の作成支援、目的外使用許可等の行政処分へ。

ライセンス数を増やさず対象文書のみ拡張できる

B

サードパーティリスク管理

契約の相手方そのものにリスクスコアを付与し、継続的に監視する方向へ拡張する。

ServiceNow を基盤とする構成と親和性が高い

C

普通財産台帳との統合

貸付中でない普通財産を自動抽出し、外部公表と問い合わせ窓口につなげて未利用地の掘り起こしを行う。

B と組合せ、申込段階でリスクスコアを参照できる

拡張時には、シングルリージョン構成・非同期キューイングなしといった現行規模を前提とした設計判断を、改めて検討する必要がある。

本質は土地貸付専用システムではなく、契約・文書リスク統制の基盤である点が主張です。

13導入ロードマップ

精度検証から段階的に適用範囲を広げる

  1. Phase 0　3 ヶ月

    PoC

    少数のサンプル契約で AI リスク抽出の精度を検証し、既存担当者のレビューにより実用可能性を判断する

  2. Phase 1　6 ヶ月

    パイロット運用

    一部所管課に限定して実運用。却下理由の蓄積と精度モニタリングを本格運用し、プロンプトを継続調整する

  3. Phase 2　本稼働

    全庁展開

    用地管財部門・契約部門の全案件に適用し、KPI による効果測定を開始する

  4. Phase 3　半年〜1 年後

    拡張検討

    対象文書の横展開、サードパーティ管理、普通財産統合の実現可能性を検討する

PoC で精度を見極め、パイロットで運用を固めてから全庁展開する段取りです。
